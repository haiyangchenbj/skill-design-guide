## 审查结论

| # | 问题 | 严重度 | 来源原则 |

| 1 | 4个Agent的职责边界模糊 | **高** | Anthropic: 明确职责边界 |

## 问题1：4个Agent的职责边界模糊（高）

### 现状

当前设计：

```
📋 选题策划    知识库更新+行业信号+内容日历 → 选题建议+优先级
✍️  内容创作    长文/短文/SEO优化，按任务参数切换
🔄 渠道适配    核心稿 → 各渠道版本
📊 效果分析    追踪渠道数据 → 月度报告 → 选题优化
```

### 问题

**内容创作Agent承担了太多角色。** "长文/短文/SEO优化，按任务参数切换"——这意味着同一个Skill要处理2000字技术博客、200字社交帖、客户案例、产品更新等完全不同的写作任务。参数切换在理论上可行，但实际上不同文章类型的提示词、参考文档、质量标准差异很大。

**选题策划和效果分析的触发场景重叠。** 效果分析产出"选题优化建议"，选题策划基于"行业信号+内容日历"产出选题——谁负责最终的选题决策？

### 建议

重新划分边界，遵循Anthropic的"路由"模式：

```
📋 选题策划 — 不变，但输出更明确
   输入：知识库变更 + 日报信号 + 内容日历 + 效果数据
   输出：选题brief（明确：文章类型/目标产品/目标读者/素材指引/目标渠道）
   人工确认后，brief传给下游

✍️  内容创作 — 只负责长文（技术博客/案例/产品解读）
   输入：选题brief + 知识库条目 + 品牌规范
   输出：1500-3000字核心稿 + 预审清单
   不负责社交帖和短内容

🔄 渠道适配 — 负责核心稿→多渠道版本（含短内容）
   输入：核心稿 + 渠道规范
   输出：公众号版/社区版/社交帖(中+英)/销售一页纸
   社交帖和短内容归这里，不归创作Agent

📊 效果分析 — 改名为"质控与分析"
   输入A（预审）：核心稿/适配稿 + 知识库 + 敏感词表
   输出A：预审报告（事实核查+合规检查+格式检查）
   输入B（月度）：各渠道效果数据
   输出B：月度报告 + 选题优化建议（反馈给选题Agent）
```

**关键变化**：内容创作只做长文，社交帖归渠道适配。效果分析增加预审职能（评估器-优化器模式）。

## 问题2：缺少护栏和失败处理设计（高）

### 现状

审批分级（L1/L2/L3）设计了人工介入点，但**Agent自身的输出护栏没有设计**。

### 缺失的护栏

**输出过滤（必须有）**：

| 检查项 | 规则 | 处理方式 |
|--------|------|---------|
| 客户名称泄露 | 月报来源的客户名称不得出现在输出中 | 自动扫描，命中则标红+阻断输出 |
| 内部代号 | DataClaw等未确认产品不可出现 | 维护禁用词表 |
| 未验证的产品能力 | 月报roadmap信息需确认官网已上线 | 知识库中标注"内部/公开"属性 |
| 竞品点名 | 不直接提及竞品名称 | 自动替换为"某友商平台" |
| 产品名称规范 | 必须使用官网正式名称 | 维护正式名称映射表 |

**失败处理（必须有）**：

| 失败场景 | 处理方式 |
|----------|---------|
| 知识库中找不到对应产品信息 | 停止生成，报告"素材不足，需补充知识库" |
| 月报案例无法确认授权状态 | 默认脱敏输出，标注"需确认授权" |
| 生成内容超过目标字数50%以上 | 自动压缩或要求重新生成 |
| 引用的数据在知识库中标注为"已过期" | 告警，不引用过期数据 |

### 建议

在每个Skill的SKILL.md中加入明确的`## 硬性规则`和`## 失败处理`章节。这不是可选项——Anthropic原文："对于高风险应用，考虑实现多层次的防护机制。"

## 问题3：知识库引用缺乏可追溯性（中）

### 现状

设计中提到"Agent基于知识库产出核心稿"，但**没有定义Agent如何报告它引用了知识库的哪些条目**。

### 问题

LangChain警告：

> "Agent Bug不是程序崩溃（显性），而是看起来通顺但完全虚构的内容（幻觉）。"

如果不知道Agent引用了哪些知识库条目，文章中的数据出了问题，无法判断是知识库数据错了还是Agent自行编造了。

### 建议

内容创作Agent的输出格式增加引用追溯：

```markdown
## 文章正文
...腾讯云弹性 MapReduce 的 TPCDS 性能提升2.7倍...

## 引用来源（内部使用，不随文章发布）
| 段落/数据点 | 知识库条目 | 来源文档 |
|------------|-----------|---------|
| "TPCDS性能提升2.7倍" | Meson产品条目 | DIaaS CSDN文章 2026.01.22 |
| "运维效率提升80%" | 努比亚案例 | 月报1月刊（📋脱敏） |
| "30+开源组件" | EMR产品条目 | 白皮书 |
```

每篇文章带一份引用表，review时可以快速验证每个数据点的出处。

## 问题4：未区分工作流步骤和Agent决策点（中）

### 现状

设计中的流程图把所有步骤串在一起，没有区分"固定步骤"和"需要LLM判断的步骤"。

### 问题

Anthropic明确指出：工作流中并非每一步都需要LLM。能用确定性代码做的就用代码做——更快、更便宜、更可靠。

### 内容创作Agent的流程审查

| 步骤 | 当前设计 | 是否需要LLM | 建议 |
|------|---------|------------|------|
| 读取选题brief | Agent读取 | ❌ 不需要 | 确定性：直接读取文件 |
| 读取知识库对应条目 | Agent搜索 | ❌ 不需要 | 确定性：brief中已指定产品名，按名查找 |
| 读取品牌规范 | Agent读取 | ❌ 不需要 | 确定性：固定路径文件 |
| 判断文章类型→选模板 | Agent判断 | ⚠️ 可以不需要 | brief中已明确类型，直接路由 |
| **写作** | Agent生成 | ✅ **需要** | 核心LLM任务 |
| **自检** | Agent检查 | ✅ **需要** | 检查事实/合规/格式 |
| 保存文件 | Agent写入 | ❌ 不需要 | 确定性：写入固定目录 |
| 生成引用表 | Agent整理 | ✅ **需要** | 需要LLM整理引用关系 |

**结论**：8个步骤中只有3个真正需要LLM。其他步骤可以用脚本或确定性逻辑处理。

### 建议

在SKILL.md中明确标注哪些步骤是"读取"（确定性），哪些是"生成"（LLM）。减少不必要的LLM调用可以提升稳定性和速度。

## 问题5：references加载策略未设计（低）

### 现状

设计中references目录包含：知识库、品牌规范、渠道规范、过往文章等。但没有定义**什么时候加载哪些文件**。

### 问题

如果Skill触发时把所有references全部加载到上下文中：
- 产品知识库（v2）已经很大
- 加上品牌规范、渠道规范、过往文章
- 上下文可能被非必要信息挤满，降低生成质量

Anthropic Skill指南明确推荐"渐进式加载"。

### 建议

SKILL.md中按步骤指定读取哪些文件：

```markdown
### Step 2: 读取素材
- 读取 `references/knowledge-base/products/{产品名}.md`（仅对应产品）
- 读取 `references/brand-rules.md`（每次都读，很短）
- 读取 `references/templates/{文章类型}.md`（按brief中的类型选择）
- 不要读取其他产品的知识库条目
- 不要读取过往文章（除非brief中明确要求参考某篇）
```

## 修改后的推荐架构

```
┌─────────────────────────────────────────────────────────┐
│                                                         │
│  📋 content-planner（选题策划）                           │
│  模式：路由                                              │
│  输入：知识库变更 + 日报信号 + 日历 + 月度效果            │
│  输出：选题brief（类型/产品/读者/素材/渠道）              │
│  人工确认 ✋                                             │
│                                                         │
│          ↓ brief                                        │
│                                                         │
│  ✍️  content-writer（内容创作）                           │
│  模式：提示链                                            │
│  步骤：读brief → 读知识库(指定产品) → 读模板 →            │
│       写作(LLM) → 自检(LLM) → 输出核心稿+引用表         │
│  护栏：客户脱敏/产品名规范/禁用词/数据出处               │
│  只做长文，不做社交帖                                    │
│                                                         │
│          ↓ 核心稿                                       │
│                                                         │
│  🔄 content-adapter（渠道适配）                           │
│  模式：并行化                                            │
│  输入：核心稿 + 各渠道规范                               │
│  输出：公众号版/社区版/社交帖(中+英)/一页纸              │
│  社交帖和短内容归这里                                    │
│                                                         │
│          ↓ 所有版本                                     │
│                                                         │
│  📊 content-reviewer（质控与分析）                        │
│  模式：评估器-优化器                                     │
│  职能A-预审：事实核查+合规+格式 → 预审报告               │
│  职能B-月度：渠道效果 → 月报 → 选题建议 → 反馈planner   │
│  人工确认 ✋                                             │
│                                                         │
└─────────────────────────────────────────────────────────┘
```

| 优先级 | 修改项 | 工作量 | 影响 |
|--------|--------|--------|------|
| **P0** | 在content-writer SKILL.md中加入护栏规则和失败处理 | 0.5天 | 防止客户名泄露/数据编造 |
| **P0** | 定义content-writer的输出格式（含引用追溯表） | 0.5天 | 可验证性 |
| **P1** | 重新划分创作vs适配的职责边界（长文vs短内容） | 设计调整 | 质量稳定性 |
| **P1** | 标注每步是确定性还是LLM，减少不必要的LLM调用 | 设计调整 | 速度+稳定性 |
| **P2** | 设计references加载策略 | 0.5天 | 上下文效率 |
